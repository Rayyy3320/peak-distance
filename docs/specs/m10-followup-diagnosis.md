# M10 后续排查：旧空会话与浮动白屏

2026-10-03。状态：0.4.2 已修复删除反馈和通信异常收尾，补齐浮动文档诊断与手动恢复；白屏直接触发事件仍未定位。实现与验收见 [后续修复记录](m10-followup-verification.md)。下文保留修复前的诊断事实。

## 用户实机现象

- 0.4.1 历史中仍有大量“新对话 · 0 问”；Delete 能展开 Confirm，再确认感觉没有变化。
- 用户已在扩展管理中重新加载扩展、刷新原网页并重新打开面板，不把“未重载”作为本次解释。
- 切到浮动后，停留当前网页、不切标签或刷新，过一会内部内容消失；截图中米白外壳与拖动条仍在。
- 本轮 Chrome 标签库存及 X 页面一度可读；打开浮动面板后工具被 Chrome 以另一个扩展 UI 正在打开为由阻止，未取得该次删除请求或白屏现场日志。没有替用户确认删除或读写用户数据库。

## 已确认的事实

### 1. 新版本没有处理已有空记录

[M10 spec](m10-chat-and-popup-interactions.md) 明确保留旧记录、不自动批量清理；`lib/db.ts:listChats` 继续返回它们。修复“以后不自动创建空会话”不会让旧空记录消失。这是此前方案的范围缺口，不能把历史仍有空记录直接等同于新版正在重复创建。

### 2. 本地正常链路可以删除旧空记录，反馈却不明确

隔离页面导入当前真实 `chatView.ts`、`deleteButton.ts`、`chatService.ts`、`chatWorkspace.ts` 和 `db.ts`，使用浏览器真实 IndexedDB；仅扩展通信和 session 存储用测试替身。放入 20 条具有不同 ID 的同名旧空记录，从真实按钮逐条 Delete → Confirm。

结果：每次处理返回 `ok:true`，数据库与列表从 20 递减至 0；删除后经过轮询未补回，最后显示“还没有历史对话”。这排除了正常链路中“旧空记录一律删不了”的断言，但不证明用户实机删除已成功。

在列表未删空时，下一条相同文本直接补位；现有 UI 没有成功反馈或会话总数，视觉上几乎不变。这是可复现的反馈缺陷，是否解释用户当次无响应尚未确定。

### 3. 删除通信异常有未收尾路径

`chatView.ts:send` 的 Promise 内直接调用 `browser.runtime.sendMessage`；同步抛错会使 Promise reject。历史行删除先禁用按钮，后续只处理 `.then(result)`，没有 rejection 的失败提示和按钮恢复。

隔离通信入口在 `chatDelete` 时受控抛出 `Extension context invalidated` 类型错误，结果为未处理的 Promise rejection、记录仍在、Delete 长期禁用、行内失败提示为空。现有验收注入的是数据库错误并返回 `{ok:false}`，没有覆盖通信 Promise reject 路径。

这证明该异常路径会造成无反馈的删除失败；**尚无实机日志证明用户这次遇到的就是该错误**。不据此断言扩展上下文已失效。

### 4. 浮动外壳无法识别旧 ready 已过期

`shared/floatingPanel.ts` 只在初始化时令 `frameReady=false`，接到 ready 后永久保持 true。再次 show 时直接返回成功，没有随 iframe 新文档或失效重置的路径；外壳也没有加载失败提示和可用的恢复入口。

因此“外壳存在”不能证明其内部工作区可用，失效后再次打开可能仍被判为成功。该缺口会妨碍恢复，但并不证明它是首次白屏的触发源。

不能把白屏直接归因于 worker 休眠、标签切换、全屏搬移或用户重载。用户明确没有相应操作，当前也没有 iframe 导航、资源失败或渲染进程异常的现场证据。

## 建议的最小修复范围

1. **先使失败可见。** 删除的 `{ok:false}`、空响应及 Promise reject 进入同一个局部失败收尾：保留记录、恢复按钮、展示错误；技术原因留本地日志。不自动重试删除，不增加全局锁或操作队列。成功后给简短“已删除”反馈，并显示历史总数，消除同名条目补位的歧义。
2. **核实白屏再修触发点。** 只记录当前工作区必要诊断：iframe 加载／就绪阶段、真实文档身份、消息失败原因和版本，不记录 Key、问题正文或材料。复现静置过程，区分 iframe 文档消失、资源加载失败和界面初始化／恢复异常；根据实际证据修相应入口。就绪状态跟随当前 iframe 生命周期，未就绪显示外壳内错误和明确重试入口，不用固定时间自动重载去掩盖问题或丢弃输入。
3. **单独处理历史污染。** 建议一次性清理严格纯空的旧记录：没有消息、非空草稿、材料快照、引用或来源内容。先报告符合条件的数量再执行；有内容的零问旧记录保留。不要简单按 `questions===0` 删除，也不要靠列表过滤冒充已清理。本轮仅提出范围，未执行清理。

## 验收补充

- 旧空记录用不同 ID 验证删除数与数据库读回；失败保留，成功恰好减少一条，多个轮询后不增加。
- 增加一个通信 reject 检查，与已有数据库失败返回检查分别验证；无需扩成每种 API 错误的测试矩阵。
- 真实 Chrome 浮动面板静置到超过用户复现时长，确认 UI 与删除仍可用；捕获白屏触发日志，验证对应修复与一次恢复。受控页面运行正常不能替代该实机检查。
- 保留既有固定／浮动移交检查；不重跑无关 AI 供应商或字幕网络专项。

本地复现材料位于 `.upstream/m10-delete-diagnosis/`：`entry.ts` 复用实际模块并生成隔离数据；`server.mjs` 提供本地测试页。`?failure=disconnect` 为显式受控错误，不代表采集到用户实际异常。该目录不参与产品构建。
